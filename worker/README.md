# Support Hub monitoring backend

A Cloudflare Worker with a D1 database. It receives telemetry from NXT LVL
applications, groups failures into incidents, polls health endpoints, and
serves the Support Hub UI and dashboard API from the same origin.

Support Hub knows nothing application-specific. Every application plugs into
the same contract: register the application and an environment, issue a
telemetry key, push events, and register health checks.

## Concepts

| Table | Purpose |
|---|---|
| `applications` | Registered applications; `id` is the slug producers send (`clientflow`). |
| `application_environments` | `production` / `staging` / `development` per application. |
| `telemetry_keys` | One credential per application environment. Only the SHA-256 is stored. |
| `events` | Normalized telemetry, whitelisted fields only. Unique on `(application_id, event_id)`. |
| `incidents` | Grouped failures. One open incident per fingerprint. |
| `incident_events` | Which events belong to which incident. |
| `health_checks` / `health_results` | Polled HTTP checks and their results (kept 30 days). |

**Event vs incident.** An `error` event's fingerprint is
`application:environment:component:ERROR_CODE`. Events that share a
fingerprint fold into the one open incident (occurrence count, first/last seen,
highest severity). Resolving an incident closes it; a later matching event
opens a new incident. `warning` and `info` events are stored but never open
incidents.

**Environment status** (`healthy` / `degraded` / `down` / `unknown`) is derived
when read:

- `down` if any enabled check's latest result is down.
- `degraded` if any check is degraded or a **critical** incident is open.
- `unknown` if there are no checks, a check has not run yet, or a result is
  stale (older than 3× its interval, minimum 5 minutes).
- `healthy` only when every check is fresh and up.

A stalled poller therefore never reads as healthy.

## Telemetry contract v1

`POST /api/v1/events`, sent with `Authorization: Bearer shk_…` and
`Content-Type: application/json`. The body may be at most 16 KB.

```json
{
  "schemaVersion": "1.0",
  "eventId": "3f1c2b9a-1d2e-4f5a-8b6c-7d8e9f0a1b2c",
  "timestamp": "2026-10-15T21:30:00Z",
  "application": { "id": "clientflow", "environment": "production", "version": "2026.10.15" },
  "type": "error",
  "severity": "error",
  "source": { "service": "clientflow-api", "component": "intake" },
  "error": { "code": "INTAKE_SUBMISSION_FAILED", "message": "Unable to persist intake submission" },
  "context": { "requestId": "…", "route": "/public/intake/submit", "method": "POST", "statusCode": 500, "durationMs": 120 }
}
```

| Field | Rule |
|---|---|
| `schemaVersion` | Required, `"<major>.<minor>"`. Major ≠ 1 → `400 UNSUPPORTED_SCHEMA_VERSION`. |
| `eventId` | UUID generated by the producer. Reuse it on retries. |
| `timestamp` | ISO-8601 with offset; at most 5 minutes in the future. |
| `application.id` / `.environment` | Must match the key's application environment, else `403`. |
| `type` | `error` \| `warning` \| `info`. `error` requires `error.code`. |
| `severity` | `critical` \| `error` \| `warning` \| `info`. |
| `source.service` / `.component` | 1–64 chars `[A-Za-z0-9._-]`, stored lowercase. |
| `error.code` | `UPPER_SNAKE_CASE`, 2–64 chars. `error.message` ≤ 500 chars. |
| `context` | Only `requestId`, `route`, `method`, `statusCode`, `durationMs`, `operation`. |

Responses:

- `202 {accepted, duplicate:false, eventId, incidentId}`: stored.
- `200 {accepted, duplicate:true}`: this `eventId` was already stored, nothing changed. The first copy wins.
- `400` / `401` / `403` / `413` / `415`: rejected. Do not retry a 4xx.

Unknown fields are dropped, never stored, and listed in `ignoredFields`. This
keeps minor versions additive.

**Never send** client names, emails, intake answers, contracts, tokens,
passwords, or headers. Send route templates (`/s/:token`), not concrete
paths. As a backstop, Support Hub redacts emails, bearer tokens, JWTs, query
values, and token-like strings from messages, and token-like path segments
from routes.

**Producer rule:** telemetry must never block or fail the application. Send it
fire-and-forget with a short timeout, and drop it if Support Hub is
unavailable.

## Dashboard API (Cloudflare Access)

| Method | Path |
|---|---|
| GET | `/api/v1/applications`, `/api/v1/applications/:id`: applications with environment status |
| POST | `/api/v1/applications` `{id, name, description?}` |
| POST | `/api/v1/applications/:id/environments` `{environment, baseUrl?}` |
| GET/POST | `/api/v1/environments/:envId/keys`: POST returns the token **once** |
| POST | `/api/v1/keys/:keyId/revoke` |
| GET/POST | `/api/v1/environments/:envId/health-checks` `{name, url, expectedStatus?, timeoutMs?, intervalSeconds?, degradedLatencyMs?, authSecretName?}` |
| PATCH | `/api/v1/health-checks/:id`: any of the fields above, plus `enabled` |
| GET | `/api/v1/health-checks/:id/results?limit=` |
| GET | `/api/v1/incidents?status=open\|resolved\|all&applicationId=&environment=&before=&limit=` |
| GET | `/api/v1/incidents/:id`: incident plus recent events |
| POST | `/api/v1/incidents/:id/resolve` |
| GET | `/api/v1/event-log?applicationId=&environment=&type=&before=&limit=` |
| POST | `/api/v1/probe` `{url, expectedStatus?, authSecretName?}`: one-off server-side check, nothing stored |
| GET | `/api/v1/environments/:envId/connection`: connection report from the latest results (runs nothing) |
| POST | `/api/v1/environments/:envId/verify`: runs every health check now (recorded like polling), then reports |

Public: `GET /api/v1/health`, Support Hub's own liveness check (including the database).

## Onboarding an application

Use **Add Program** in the Support Hub UI (the program switcher's `+`). The
wizard collects the program's info, API base URL (https), the health checks to
poll, and which of them need a bearer token (an `HC_*` Worker secret). Then it:

1. registers the application (its slug becomes the telemetry `application.id`),
2. registers the environment (`dev` in the UI maps to `development`),
3. adds the health checks,
4. issues a telemetry key, shown **once** with the env snippet to paste into
   the application's server environment.

A failure stops at that step and nothing is added to the program list. Retry
reuses whatever was already created, so re-running is safe. **Test Connection**
runs through `POST /api/v1/probe`, so it checks reachability from Support Hub
the same way polling will, not from the browser.

For ClientFlow: slug `clientflow`, base URL `https://clientflow-vjqd.onrender.com`,
checks `live` `/api/v1/health/live`, `ready` `/api/v1/health/ready` and
`dependencies` `/api/v1/health/dependencies` (requires token,
`HC_CLIENTFLOW_PROD`, whose value is ClientFlow's `HEALTH_DEPENDENCIES_TOKEN`).

## Verifying a link

An environment is **connected** when both of these hold:

- **health:** every enabled check answers (up or degraded);
- **telemetry:** the app has delivered at least one event with a key that is
  still active. ClientFlow sends an `info` `TELEMETRY_CONNECTED` event on
  startup for exactly this; it opens no incident.

Health alone gives **partial**; neither gives **not connected**. The wizard's
last screen and each program's **Settings → Monitoring** card show this live,
and keep watching for the first event. Programs added before onboarding did
real signup show **Finish linking** there.

### From the command line (scripts, agents)

Each application ships a `support-hub.json` manifest (ClientFlow's is at the
root of its repo). Link and verify it with:

```sh
SUPPORT_HUB_URL=https://<support-hub-domain> \
CF_ACCESS_CLIENT_ID=<service token id> CF_ACCESS_CLIENT_SECRET=<service token secret> \
npm run link-program -- ../clientflow-hub/support-hub.json --environment production --wait 600
```

It's safe to re-run: existing records are reused, and a key is issued only if
the environment has no active one (`--new-key` forces one). It exits 0 when
connected, 2 when partial, and 1 otherwise. The service token comes from Zero
Trust → Access → Service Auth, and the dashboard Access application needs a
**Service Auth** policy that allows it.

## Deploying

1. `npx wrangler d1 create support-hub`, then put the printed id into `wrangler.jsonc`.
2. `npm run db:migrate:remote`
3. Add a custom domain for the Worker. `workers_dev` is disabled because a
   `workers.dev` URL would sit outside Access.
4. Cloudflare Zero Trust → Access:
   - A self-hosted application for the whole domain (your team's emails).
   - A **Bypass** application for `<domain>/api/v1/events` and
     `<domain>/api/v1/health`. Ingestion is authenticated by telemetry key,
     and Access bypass rules match by path, not method. That's why the
     dashboard reads events from `/api/v1/event-log`.
5. `npx wrangler secret put ACCESS_TEAM_DOMAIN` (e.g. `https://<team>.cloudflareaccess.com`)
   and `npx wrangler secret put ACCESS_AUD` (the AUD tag of the dashboard
   application). Without both, dashboard APIs return `503 AUTH_NOT_CONFIGURED`.
   The Worker verifies the Access JWT itself, in addition to Access at the edge.
6. `npm run deploy`

A check is `up` when the response status matches `expectedStatus`. An endpoint
can report its own verdict with an `X-Health-Status: degraded` (or `down`)
response header; ClientFlow's `/api/v1/health/dependencies` does this when a
pipeline such as email is impaired.

Authenticated health checks take their bearer token from a Worker secret named
`HC_*` (e.g. `npx wrangler secret put HC_CLIENTFLOW_PROD`). Reference that
name in `authSecretName`. Only `HC_*` names are accepted, so a check can never
send any other secret. A missing secret records the check as `down` with
`errorType: "config"`.

## Local development

```sh
npm run db:migrate:local
npm run build
npx wrangler dev --local --var AUTH_DEV_BYPASS:true --test-scheduled
# trigger a polling tick:
curl "http://localhost:8787/cdn-cgi/handler/scheduled?cron=*+*+*+*+*"
```

`AUTH_DEV_BYPASS` only works for requests to `localhost`.

## Tests

`npm run test:worker` runs the worker suite in Node against a real D1
(SQLite) database from Miniflare. It covers ingestion, idempotency, incident
grouping under concurrency, Access JWT verification, redaction, and health
scheduling.
